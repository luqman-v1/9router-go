# Technical Debt Register

This register covers verified, still-open risks in `9router-go` v1.9.16-exp.1.

**Register hygiene (DOC-01).** This file drifted: it still declared `v1.9.1` and listed DB-02, OPS-01 and DATA-01 as open long after their fixes landed. A register that overstates open risk sends the next reader auditing work that is already done, and one that understates it hides live risk — so each row below was re-verified against the current tree before this revision, and the three stale rows were closed with the evidence that closed them. It supersedes the former declarations that no critical, high, or medium debt existed. “Resolved” work from the changelog is not listed here unless it explains a remaining limitation.

Severity reflects operational impact if the condition occurs, not likelihood:

- **High** — can break startup/data integrity, expose sensitive data, or replace an executable from unverified input.
- **Medium** — can lose data, weaken verification, hang OAuth operations, or make performance/feature claims unreliable.
- **Low** — bounded maintenance or diagnostics gap with limited direct impact.

| DB-01 | Resolved in `internal/db/schema.go` (`EnsureCoreSchema`, wired in `ProvideDatabase`) | **Was:** no production core-schema bootstrap; blank DB started but failed later on missing tables. **Now:** startup creates the 11 upstream tables/indexes when absent, backfills missing columns, seeds `_meta.schemaVersion='1'` + empty settings row — all idempotent. Covered by `TestEnsureCoreSchema` (tables, seeds, fresh-install flow, idempotency, legacy backfill) + live fresh-`DATA_DIR` smoke. | DB-02 | Resolved in `internal/db/vault.go` + `internal/vault/` | **Was:** credentials were plaintext in `providerConnections.data`, `apiKeys.key` and other JSON, and the dashboard export carried them. **Now:** an optional AES-256-GCM envelope vault seals credentials before every data write (`UpdateConnectionData` seals before the write, so a credential is never briefly readable) and hydrates them on read; it is inert when `ROUTER_MASTER_KEY` is unset. | OPS-01 | Resolved in `internal/updater/updater.go` | **Was:** SHA-256 was verified only when `expectedSHA256` was non-empty, so a manifest with no hash let the updater replace the running binary from unverified input. **Now:** a manifest carrying no sha256 is a dead end — `PerformSelfUpdate` refuses it and the GitHub Releases fallback supplies version metadata only, never an unverified binary. Remaining: the GitHub fallback still has no signed checksum or attestation, so a release published without a manifest hash is refused rather than trusted, which is the safe direction but not a verified supply chain. |
| VER-01 | Resolved in `.github/workflows/ci.yml` (`race` job) | **Was:** CI ran `go test ./... -v` but not `go test -race ./...`, so the “race-clean” statement was not maintained. **Now:** a dedicated `race` job runs `go test -race -count=1 -timeout 10m ./...` on every PR, and `make test-race` reproduces it locally. Remaining: the job is `ubuntu-latest` only — there is still no macOS or Windows race runner, so a race that depends on a specific OS is not covered. |
| DATA-01 | Resolved in `internal/db/usage_retention.go` + `usage_retention_loop.go` | **Was:** `requestDetails` kept every diagnostic row forever with no pruning. **Now:** `PruneRequestDetails` bounds both age (`retentionDays`) and row count (`maxRows`), runs on a timer from `StartRetentionLoop` (wired in `internal/app/server.go`), and never touches the billing ledger. Remaining: content is still written before it is pruned, and there is no redaction of secret-like strings inside a stored message — retention bounds how long it lives, not what it holds. |
| OAuth-01 | Resolved in `internal/handlers/oauth/` | **Was:** `device.go` and its siblings built requests with `http.NewRequest`, so client cancellation, shutdown and deadlines had nothing to cancel — a hung-up client left a goroutine and an upstream connection parked until the 15s client timeout. **Now:** every outbound call in the device flow carries the caller's context. `postJSON`, `postForm` and `getJSON` take a `ctx` first parameter, the per-provider start/poll wrappers thread it through, and the nested helpers (`glmResolveCodingPlanKey`, `glmExchangeBusinessToken`, `museAccountEmail`, `museMintKey`, `kiroProfileArn`, `validateKiroAPIKey`) do too. ## Accepted limitations

These are operational or compatibility constraints, not claims that the risk has been eliminated:

1. **One active Go writer is the supported model.** SQLite may still be opened/read by a separate upstream process for controlled migration or inspection, but coordinated HA writers are not a supported topology. This is distinct from DB-03, which tracks accidental lost updates in shared-write deployments.
2. **Local-owner filesystem protection is the credential baseline.** `0700` on the immediate DB directory and `0600` on the main DB reduce access, but do not provide encryption, ACL management, or backup protection.
3. **OIDC/SAML configuration is partial.** The current server exposes OIDC/SAML tests and SAML metadata, but the Svelte UI advertises start routes that the Go router does not mount. Until implemented end to end, password login is the supported SSO-free path.
4. **The dashboard JSON export is configuration-only.** It intentionally omits usage history, daily aggregates, request details, leases, and upstream metadata; a physical SQLite backup is required for full recovery.
5. **Historical benchmark numbers are retained as historical context only.** They are not acceptance criteria or current release measurements.
6. **Provider behavior is conditional.** A route or catalog entry does not guarantee identical credentials, quotas, cloaking, or upstream response behavior across releases.

## Recently resolved, but not proof of zero debt

The changelog records fixes for stream state isolation, request-body bounds, response-body closure, graceful shutdown, OAuth error-body truncation, DB file permissions, registry synchronization, and MITM lifecycle races. Those are useful mitigations, but they do not replace CI race coverage, schema versioning, updater verification, retention policy, or two-process tests described above.
