# `free-pi` provider — session-as-API for 9router-go

## What we are building

A new first-class provider, `free-pi`, that turns free-pi's CLI-only account into a multi-client API
behind this gateway. Plain `[OI]` Chat Completions upstream. The hard parts are **session identity** (an
account tolerates **4** concurrent sessions, and we should occupy one of them, not drift upward) and
**advertising** (upstream may gate on ad impressions — see §1 and §4).

Decision locked with the operator: **`fp` / `free-pi`**, login via **OAuth device flow (abstracted from
the user)**, `x-session-id` **stable per account**, and session conflicts resolved by **reset-once +
retry-once — never a reset loop, and never silently killing a live CLI**.

Two premises from the first draft were wrong and are corrected in §1: the cap is 4 (not 1), and headless
use may require an ad subsystem. The first makes the feature *smaller*; the second is the one thing
awaiting your decision.

## Reference research (done, not assumed)

Three cited repos, and they are *not* equivalent — this matters:

| Repo | What it actually is | Verdict |
|---|---|---|

It explicitly **refuses** to forward to the remote API, forwards only the *latest user message* (no system prompt, no history), buffers the whole answer, and returns 409 while busy. | **Rejected.** A server-side gateway has no CLI process to drive. Its own design notes say direct forwarding is "intentionally unsupported". |
| `dennisonbertram/free-pi-cli` | The real CLI. `src/provider.ts` registers an `openai-completions` provider at `{base}/v1` with a Bearer JWT plus `x-session-id` / `x-client-version`. | **This is the specification.** We implement the same wire contract as a second client. |
| `hungkevin/free-pi-cli-proxy` | A **working** [OI]-compatible proxy for `api.freepi.ai` (Node/Express, MIT). Same target as this feature. | **Primary behavioural cross-check.** It contradicts two of our assumptions — see below. |

### What the third repo corrects

`hungkevin/free-pi-cli-proxy` is the closest thing to prior art (same goal, same upstream), and reading
its source overturned two premises this plan was built on. Both corrections are already folded in below.

**1. The session cap is 4, not 1.** `server.mjs:958` — *"free-pi.ai 限制每個帳號最多 4 個並行
session，超過會回 409"* — and the upstream message is *"You've already got 4 free-pi CLI sessions
running"*. So `concurrent_session` does **not** mean "someone else is using your account"; it means
*"this account already has 4 live sessions"*. The "limit one session per account" premise is wrong, and
that shrinks this feature substantially: the strict serialization, the mutex striping and the
cross-process lease were all buying protection against a limit four times tighter than reality. A stable
session id per connection reuses the **same** session on every request, so `409` becomes rare rather than
routine.

**2. Headless use may require the Gravity ad subsystem.** `server.mjs:294` — *"上游伺服器檢查「廣告展示
記錄」而不只是「有 gravity session」"* — upstream checks **ad impression records**, and
`GRAVITY_DISABLE_PIXEL=1` is documented as *"可能導致 403 廣告錯誤"* ("may cause 403 ad errors"). The
flow it implements is: init the `@gravity-ai/api` pixel → `GET /ads/next?slot=banner` → `GET imp_url`
(Gravity impression pixel) → `POST /ads/impression {ad_id, click_token, imp_fired:true}`, plus an
`x-gravity-context` header (base64url of `{sessionId, user:{userId: sha256(jwt.sub), gruid, grclid,
graid}}`) on every request, refreshed every 10 min.

This is a real scope item with two hard consequences, and it is the one part of the design **I will not
decide silently**:

- **There is no Go port.** `@gravity-ai/api` is an npm package; reimplementing its session/visitor-ID
  handshake in Go is a reverse-engineering task of its own, and it would be the largest single chunk of
  this feature.
- **The reference implementation reports impressions that were never displayed.** `imp_fired: true` is
  posted for an ad no human saw, every 10 minutes. That is misreporting to the advertiser who paid for
  it — the revenue that funds the inference. I am not willing to build that quietly. The honest variants
  are to actually render the banner in the dashboard (so the impression is true), or to skip ads and
  surface the resulting 403 plainly.

Decided: option A, rendered honestly — see §4 and the resolved decisions at the end.

Other confirmations from the same source, all consistent with §1:

- **Pure passthrough works.** No TLS fingerprinting, no request-shape checks on `api.freepi.ai` —
  *"上游無 TLS 指紋閘門、無請求形狀檢查"*. No cloaking/prompt-spoofing machinery is needed, unlike
  `opencode`.
- **`x-client-version` floor is ≥ `0.6.2`**, recommended `0.6.14`+; the reference's own default of
  `0.4.10` is below the floor, which is a real-world confirmation that ignoring `min` bricks the provider.
- **429 has a taxonomy we should mirror**, because it maps cleanly onto this repo's existing connection
  locking: `rate_limit_exceeded` = hourly cap (switch account, retry immediately), while
  `creditlimitexceeded` / `insufficient_quota` / `billing_error` / `budgetlimiterror` /
  `gousagelimiterror` = daily quota exhausted (never retry the same account). Retry ≤ 4, base 2s, cap
  30s, jitter, and **fail fast when `Retry-After` > 5 min**. Prefer `retry-after-ms` over `retry-after`.
- **401 is terminal for that JWT** — clear it and require re-login; do not retry old tokens. This matches
  §4 and confirms the dead-JWT handling matters.
- **`/client-version` → `models[].id` is the request model value**, and it is refreshed every 30 min.
  Confirms §5.
- Multi-account rotation is a first-class feature there (`FREEPI_JWT_LIST`) — **we get it for free** from
  this repo's existing connection rotation, so there is no reason to port `FREEPI_JWT_LIST` at all.

## Design

### 1. Session identity — one deterministic session per account

`x-session-id` is a UUID **derived deterministically from account identity**, not minted randomly:
`uuid.NewSHA1(freePiNamespace, accountKey)`, where `accountKey` is the JWT `sub` (falling back to the
connection email). It is persisted at login in `data.providerSpecificData.freePiSessionId` purely as a
cache — the value is recomputable, so a missing field is never a problem.

Persisting per-connection state is the established pattern here: Freebuff mints a `fingerprintId` at
login and stores it the same way (`internal/handlers/oauth/freebuff.go:363-366`, read back by
`executor/freebuff.go:291-300`).

Why **deterministic** rather than random-per-connection, which is what the first draft said:

- Two rows for one account (re-login creates one; the dashboard permits a second) would otherwise yield
  two ids and burn two of the four sessions for a single account.
- Every gateway process and every restart computes the same id, so an account occupies **one** session
  no matter how many instances run. This is what makes the serialization machinery in §2 unnecessary.
- It also survived the design review's strongest objection: a *persisted* constant is useless as a lease
  value for compare-and-delete (every holder matches), but a *derived* constant is exactly what you want
  for stable identity.

### 2. Serialization — built for one session, though upstream allows four

Operator decision: **keep the conservative single-session machinery even though the cap is 4.** The
rationale is explicit — a cap of 4 today can become a cap of 1 tomorrow, and the failure mode of getting
caught without the guard is nasty (a session war across processes). So we build for the tight case and
treat the current 4 as headroom we simply do not spend.

Two layers, both modelled on Freebuff — the only provider in this repo with this problem:

- **In-process**: a bounded `[64]sync.Mutex` array striped by `hash(accountKey)`. O(1) memory, no growth,
  per-account isolation. Not a per-connection map (unbounded map keyed by a client-influenced value →
  AGENTS.md §4.G), and **not** one global mutex — Freebuff's `freebuffClaimMu` is held across a 30s
  network POST, which is global stop-the-world and should not be copied. The lock is **never held across
  the reset**: lock → check/acquire lease → unlock → reset → lock to record.
- **Cross-process**: `LeaseStore` (`internal/proxy/executor/executor.go:17-21`, `internal/db/leases.go`)
  with a new scope `LeaseScopeFreePiSession`, key via the existing `db.LeaseKey(accountKey)`
  (`internal/db/leases.go:174-179`) so raw tokens never touch the table.

Two details that must be right — both were wrong in the first draft and are worth stating because they
are counter-intuitive:

- **Lease key = account identity, not connection id.** Hashing the connection id breaks the moment an
  account has two rows (re-login creates one; the dashboard permits a second): two keys, two sessions,
  permanent war. This is why §1's id is derived from account identity too.
- **Lease value = per-process epoch, never the session id.** `ReleaseLease` is a plain
  `DELETE … WHERE value = ?` (`leases.go:163-172`), so two processes holding the same *persisted*
  session id would both match and either one's compare-and-delete would kill a sibling's live row. A
  per-process epoch minted at boot makes "is the holder me?" answerable. TTL in **seconds**, not
  minutes — `AcquireLease` only takes over already-*expired* rows (`:90-102`), so a long TTL turns one
  crash into a long block.

### 3. Conflict recovery — wait for our own, reset for stale, never loop

The third repo changed what the error *means*, which changes the right response:

| | First-draft reading | Correct reading (`server.mjs:958`) |
|---|---|---|
| 409 `concurrent_session` | "someone else holds my one session" | **"this account already has 4 live sessions"** |
| Implication | fear of stealing a human's session | a **count** problem, mostly our own stale rows |

Because we build conservatively (§2) we occupy exactly one of the four, so 409 in practice means either
our own concurrency is racing (rare, and the lease catches it) or stale sessions from earlier crashes.
Policy, in priority order:

1. **Lease live, held by another epoch** → a sibling process is mid-request. **Wait; never reset.** The
   reset would be aimed at our own legitimate request.
2. **Lease free or held by our own stale epoch** → `POST /session/reset` **once**, retry **once**. This
   is the documented remedy, used by both free-pi-cli's `/close-other-session` and the reference proxy
   (`server.mjs:1082-1090`), and it also clears the residue of a crash.
3. Per-account **cooldown** between resets, so a loop cannot form.
4. Opt-out: `freePiAutoReset:false` in `providerSpecificData` (and a global config flag) → return 409
   with an actionable message instead of resetting.
5. Dashboard **"Clear session"** button issuing `POST /session/reset` on demand.

**Residual risk, stated plainly:** `/session/reset` releases the caller's *other* sessions, so it can
terminate a human's running `free-pi-cli` on the same account. That is inherent to the endpoint, not a
choice we make; the mitigations are rules 1 and 3, plus documentation telling anyone who runs the CLI
interactively on a provider account to set `freePiAutoReset:false` or use a separate GitHub account.

**Not ported from the reference:** `FREEPI_JWT_LIST` multi-account rotation. This repo rotates
connections natively (`applyConnectionStrategy`, `internal/handlers/chat/connections.go:861-899`), so
multi-account already works the moment a user adds a second connection — and the 429 taxonomy (§7) maps
onto this repo's existing lock-and-rotate path instead of a parallel implementation.

### 4. Ads — rendered, not simulated

Operator decision: **option A.** The banner creative from `GET /ads/next?slot=banner` is rendered in the
dashboard, and `POST /ads/impression` fires **only after that creative was actually rendered**. The
reference proxy's approach — reporting `imp_fired: true` on a 10-minute timer with nothing displayed —
is explicitly not implemented: it tells the advertiser a human saw an ad when none did, and that
advertising spend is what pays for the inference this provider consumes.

Design consequences:

- Rendering is a **dashboard** surface (the gateway binary also serves the SPA), so the impression is
  attributable to a real view. Impressions are therefore **event-driven on view**, not on a timer — no
  ad shown means no impression, which is the whole point.
- `x-gravity-context` is the base64url of
  `{sessionId, user:{userId: sha256(JWT.sub), gruid, grclid, graid}}`, refreshed ~10 min. Who *generates*
  it is settled by the protocol reading in P4b below: the **browser**, not Go.
- `x-gravity-context` is sent on chat requests too (`server.mjs:937-953`). The header builder in P2 takes
  an **optional** context provider from the start, so ads absent (pixel failed, user declined) degrades
  to "requests without ad context" rather than a code change.
- If the upstream 403 `"Ads aren't showing for this account"` still appears, it is surfaced verbatim with
  a remediation hint. We do not paper over it by faking an impression.

### 5. Auth — device flow, consent shown verbatim, never auto-accepted

`free-pi`'s consent screen is not boilerplate: it discloses that **ads pay for inference, ad content
receives excerpts of the recent conversation (Gravity), and that prompts, code, files and responses are
saved as traces, used to train models, and may be shared or sold, with no opt-out after acceptance**
(`src/consent.ts`, `CONSENT_VERSION = "4"`).

So: the dashboard renders that text verbatim next to an explicit accept control, and
`POST /api/oauth/free-pi/initiate` **refuses to proceed unless consent was accepted in that request**.
We do not accept training-data consent on a user's behalf. Declining makes zero server calls — the
same invariant free-pi-cli enforces (`src/run.ts`, privacy invariant on the order of the version check).

JWT lifetime is **90 days with no refresh token**. This is the subtlest failure mode in the whole
feature, because the gateway's existing 401 machinery silently does nothing useful here:

- `fallback.go:721-761`'s reactive refresh calls `forceRefreshOAuthToken`, which requires a
  `RefreshToken` and returns "no refresh token available" — a no-op for us.
- 401 **is** retryable (`providers.go:1182`) and `isAccountAuthFailure` makes the error non-model-scoped,
  so a dead 90-day JWT lands in `LockConnectionRateLimit` with the **2-minute** rule
  (`errorclassify.go:56`): the connection cools for two minutes, retries, cools, forever, and
  `$.status` is never set — the dashboard shows a healthy connection that can never work.

So: decode the JWT `exp` locally and refuse before the call, and on a real 401 write
`$.status='error'` via `Repo.RecordConnectionScopedError` (`internal/db/accounts.go:69-94`) beside the
codex quota block at `fallback.go:772-778`, plus a long lock rather than the 2-minute default. The
dashboard then shows "re-authenticate", which is the truthful state.

### 6. Version pinning

`x-client-version` must clear the server's `min` floor or every request is refused. The reference repo
confirms the floor is **≥ `0.6.2`** today and recommends `0.6.14`+ — and its own default of `0.4.10` is
below the floor, which is a live demonstration of exactly the failure mode we must avoid. `min` is
currently unhandled anywhere in this repo except one hardcoded Grok pin
(`providers/client_identity.go:9-21`), so this is new machinery: a **provider-level** cache (single entry,
`singleflight`, ~1h TTL) for `GET /client-version`, never per connection — it is one
account-independent document. We send the server's `latest`, which also keeps us afloat if `min` rises.
Constant fallback `freePiClientVersion = "0.6.15"` (the version this contract was verified against).

### 7. Rate-limit taxonomy (adopted from the reference)

`free-pi` distinguishes two 429s, and conflating them wastes the whole retry budget on a limit that will
not clear:

- `rate_limit_exceeded` → **hourly** cap → this connection is temporarily unusable, rotation eligible,
  clear at the next hour boundary.
- `creditlimitexceeded` / `insufficient_quota` / `billing_error` / `budgetlimiterror` /
  `gousagelimiterror` → **daily** quota exhausted → never retry this account; mark exhausted until
  00:00.
- Retry policy for genuine transient 429s: ≤ 4 attempts, base 2s, cap 30s, **jitter**, and **fail fast
  when `Retry-After` > 5 min** (that is a daily-quota signal, not a blip). Prefer the `retry-after-ms`
  header over `retry-after` when present.

This maps onto what the repo already has — `ErrorRules`/`GetQuotaCooldown`
(`internal/providers/errorclassify.go:40-64`, `:112`) and the `LockConnectionModel` /
`LockConnectionRateLimit` pair (`fallback.go:215-238`) — so it is a classification addition, not a new
retry engine.

### P2 — Executor: headers + streaming passthrough
New `internal/proxy/executor/free_pi.go` + `free_pi_test.go`; register in `init.go`.

`proxy.Forward[OI]` cannot be used as-is: it has no per-request header hook (`internal/proxy/openai.go:14-31`
assembles only static headers, and `ProviderConfig` has no dynamic field). So this executor assembles
its own headers, the way `freebuff`/`opencode`/`codebuddy` already do:

- `Authorization: Bearer <key>`
- `x-session-id: <ConnData["freePiSessionId"]>`, else the same id re-derived from account identity
- `x-client-version: <ConnData["freePiClientVersion"]>` or the pinned constant
- `Accept: text/event-stream` when streaming

Body is forwarded **unrewritten** — no field added, dropped or coerced, unlike `ForwardOpencode`.
(`proxy.newJSONRequest` canonicalises every chat body for prompt-cache determinism, so the bytes on the
wire are a re-serialisation of the same JSON value; the test asserts semantic equality for that reason.)
Streaming reuses `execSSEStream` + `proxy.NewStallReaderWithContext` exactly as `freebuff.go:433-437`.

**The status check is mandatory, not optional.** `executor.Default()` (`executor/openai.go:22-40`)
never inspects `resp.StatusCode`, and `jsonResponse` always writes 200 — so registering this provider on
the default path would turn our carefully-built `concurrent_session` 409 into an HTTP **200 carrying an
error body**, with `fwdErr == nil`, recorded in `usageHistory` as a served turn. The executor must
return `*proxy.UpstreamError{StatusCode, Body}` on any non-200 before touching the response writer, as
`freebuff.go:406-429` does.

Tests (httptest fake): exact header set; body unchanged; SSE passthrough; non-stream JSON passthrough;
missing session id still produces a stable header; **a 409 upstream surfaces as a 409 to the client, not
a 200**; a mid-stream error frame is classified rather than swallowed.

### P3 — Session identity, lease + conflict policy
New `internal/proxy/executor/free_pi_session.go` + test; add `LeaseScopeFreePiSession` to
`internal/db/leases.go`.

Contents: the deterministic `accountKey` derivation (JWT `sub`, email fallback), the `[64]sync.Mutex`
stripe array, the lease acquire/read/release trio with a **per-process epoch** as value and a
short-TTL, and the §3 reset-once-retry-once path. Modelled on `freebuff_session.go` — same L1
memory-then-L2-lease shape — minus Freebuff's global mutex-held-across-POST mistake.

Table-driven tests, one row per rule — this is the highest-risk logic, so the table is the spec:

| Scenario | Expected |
|---|---|
| same account, two connections | **identical** `x-session-id` (one session, not two) |
| same account, second process | identical id; lease value differs (epoch) |
| lease held by a foreign epoch | **wait**, no reset |
| lease free / our own stale epoch, 409 | reset once → retry once → 200 |
| second 409 inside cooldown | no second reset → 409 to client |
| `{released:false}` from reset | still exactly one retry |
| reset call itself fails | 409, connection not poisoned |
| `freePiAutoReset:false` | never resets, always 409 |
| lease TTL expiry after a crash | a later caller takes over without manual cleanup |
| expired JWT (`exp` in the past) | rejected before any request is made |
| 429 `rate_limit_exceeded` | connection locked short (hourly), rotation eligible |
| 429 `creditlimitexceeded`/`insufficient_quota` | connection marked exhausted, **not** retried |
| 429 with `Retry-After` > 5 min | fail fast, no backoff loop |
| 403 `Ads aren't showing…` | surfaced verbatim, never faked |

### P4 — OAuth device flow (abstracted login)
New `internal/handlers/oauth/free_pi.go` + test; routes in `internal/handlers/router.go`
(`mountOAuthRoutes`, alongside the freebuff pair at `:370-371`).

- `POST /api/oauth/free-pi/initiate` `{consentAccepted:true}` → 400 unless accepted → `POST /auth/github/device`
  → `POST /auth/consent` (version `"4"`) → `{userCode, verificationUri, interval, expiresIn, sessionId}`
- `POST /api/oauth/free-pi/poll` `{sessionId}` → `POST /auth/token` → on token: `GET /client-version`,
  derive `freePiSessionId`, create/update the connection with
  `providerSpecificData{freePiSessionId, freePiClientVersion, freePiModels, authMethod:"device_flow"}`.
  Returns `{status:"connected", connectionId}` / `{status:"pending", retryAfter}` /
  `{status:"consent_required"}` / `{status:"expired"}`.
- Pending state in a bounded `sync.Map` with TTL sweep (mirroring `musePendingMints`).

Tests: consent gate makes **no** upstream call when declined; `retry_after` honoured; pending →
connected transition; session id persisted; 403 `consent_required` surfaced as its own status.

### P4b — Ads subsystem (option A — IMPLEMENTED)

Per §4: render the banner creative in a dashboard surface and fire the impression only on actual render.
Scope:

- **Protocol reading DONE (2026-11-09), and it changes the shape of this phase.** `@gravity-ai/api@1.2.1`
  was unpacked and read. Findings:
  - `gravityPixel({pixelId, storageDir})` is an ordinary HTTP client: `start()` opens a **session**
    against a configurable `sessionEndpoint`, and `track()` posts to a configurable `eventEndpoint`.
    It exposes `getSessionId()` (`gr_sess_…`), `getVisitorId()`, `getClickId()`, `getGraid()`.
  - `gravityContext({sessionId, user})` **collects runtime signals — user-agent, screen size, timezone,
    locale** — and in the browser path reads `window.gravityPixel` for the visitor/session/click ids.
  - **Consequence: a faithful Go port is the wrong shape.** A server-side generator cannot observe a
    screen size or a browser locale; it would have to invent them, which is the same class of dishonesty
    as the fake impression this plan already refuses. The honest architecture is **browser-driven**: the
    dashboard SPA loads the SDK, generates the context, renders the creative, and reports the impression;
    Go only needs to accept that context and forward it as `x-gravity-context`.
- So P4b is a **frontend-led phase with a thin Go receiver** — plausibly its own PR:
  - `internal/proxy/executor/free_pi_ads.go` — `GET /ads/next?slot=banner`, `GET imp_url` (restricted to
    `FreePiImpressionHosts`), `POST /ads/impression`, plus a `x-gravity-context` pass-through supplied by
    the client. No server-minted context.
  - Dashboard: an ad surface that renders the creative and calls the impression endpoint only after paint.

  Size is still not estimated here, but the unknown is now bounded: it is UI work plus ~3 HTTP calls,
  not an SDK reverse-engineering exercise.

  **Shipped as described**, with one honest limit recorded in
  `internal/handlers/dashboard/free_pi_ads.go`: `x-gravity-context` is omitted because it can only
  be produced from browser signals, so impression *attribution* is unverified even though the gate
  flow itself is implemented. Files: `free_pi_ads.go` (client + SSRF allowlist),
  `free_pi_ads_pending.go` (served-creative table), `free_pi_ads_handlers.go` (two routes),
  `FreePiAdBanner.svelte`, plus the "Clear session" action from §3 item 5.
- `GET /api/free-pi/ad` dashboard endpoint returning the current creative, and an impression endpoint the

## Risks the operator should know

1. **Headless use sits at the edge of the arrangement that funds the account.** The consent states
   inference is ad-funded and that sessions are used for training and may be shared/sold. Rendering ads
   in the dashboard (§4) keeps the ad side of that bargain honest, and the consent is shown verbatim with
   an explicit accept — but every proxied prompt still enters that training corpus, and that is a real
   consequence the operator should accept deliberately rather than discover.
2. **Issue #15 on free-pi-cli asked for exactly this** (use free-pi as a provider in another harness)
   and has not been blessed; the maintainer's stated options were a documented extension or a note that
   it is unsupported. This is an unsupported-client integration and may break without notice.
3. **No refresh token** — a 90-day JWT with no renewal path means re-login, by design.
4. **`x-client-version` is a moving floor.** If the server raises `min`, a pinned constant will start
   being refused; persisting the server's `latest` at login mitigates this only until it moves again.
5. **Lease coordination is per-DB-file.** Two gateway instances on separate volumes or hosts get *zero*
   coordination. With the conservative one-session design (§2) that is tolerable — the deterministic id
   means both still compute the same session — but the lease itself only protects same-DB deployments.
   Worth documenting rather than discovering in production.
6. **The combo path burns a request per member on 409.** Combo members `continue` past a failure and the
   lock check returns before excluding the connection (`combo.go:899-905`, `:963-968`), with no memory —
   so a permanently-stuck session costs one round trip per combo member on *every* request until someone
   clears it. Not fatal, but it argues for the dashboard "Clear session" action landing in the same PR.
7. **The Gravity work carries unbounded estimation risk** until `@gravity-ai/api`'s protocol is read.
   P4b is now implemented, but its `x-gravity-context` gap means ad *attribution* stays unverified
   against the real upstream — a live check is the only way to close it.

## Resolved decisions (from the operator)

1. **Ads → option A, rendered honestly.** The banner creative is displayed in the dashboard and the
   impression fires only after it was actually painted. The reference proxy's timer-based
   `imp_fired: true` with nothing displayed is **not** implemented — it misreports to the advertiser whose
   spend funds the inference. See §4 and P4b.
2. **Session machinery → conservative, built for one session despite the cap of 4.** The lease and the
   striped mutex are worth carrying because a cap of 4 today can tighten to 1 tomorrow, and being caught
   without the guard means a session war across processes. We therefore occupy exactly one session per
   account and leave the other three unspent. See §2.
3. **Login → OAuth device flow, abstracted from the user**, with the consent screen shown verbatim and an
   explicit per-request accept. Deliberately **not** the reference's non-TTY auto-consent: that would take
   a training-data decision on the user's behalf. See §5.
4. **Session id → deterministic per account**, not per connection, so re-login and multi-connection
   accounts converge on the same upstream session. See §1.
