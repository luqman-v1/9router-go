### fix(providers): send a Responses body on the `/responses` lane of a custom openai-compatible node

- A custom `openai-compatible` provider node whose stored `apiType` is `"responses"` had its URL moved to the `/responses` lane by `compatibleNodeLane` (`internal/handlers/chat/connections.go`), but its body was never converted: the gateway posted an OpenAI Chat Completions payload (`messages[]` plus nested tools `{type:"function",function:{name}}`) to an endpoint that accepts only a Responses payload (`input[]` plus flat tools `{type:"function",name}`). Upstreams rejected it with `function tool name is required`, and a tool-less request with `request has no system prompt or conversation content` — two symptoms of one lane/format drift, the same class as the `/messages` bug fixed in #797.
- Root cause was dispatch, not translation. `executor.Get` is an exact map lookup and a custom node's id is dynamic (`openai-compatible-responses-<suffix>`), so no registered executor could ever claim it and the request fell through to the generic Chat forwarder. `CompatibleNodeWires` leaves such a node's `Format` as the OpenAI default by design ("the lane moves, the format stays OpenAI either way"), so nothing downstream knew to translate.
- Both conversion halves already existed and are reused rather than reimplemented: `buildResponsesBody` rewrites the request (`messages`→`input`, nested tools→flat, `max_tokens`→`max_output_tokens`), and `handleCodexStream` reads the Responses reply back into Chat chunks — or relays it untouched when the client itself speaks Responses. The new `ForwardCompatibleResponses` is the same three-step shape as `ForwardGrokCLI`, minus the provider-specific headers and model rewrites a custom node does not need.
- The gate is the existing `UpstreamSpeaksResponses`, already true for a base URL ending in `/responses`, so no new table or provider-id check is introduced (§3.B). It is consulted **only** when no executor claimed the provider, leaving every registered Responses lane (`codex`, `grok-cli`, `muse`, `opencode*`) on its own executor, and is skipped for Claude-wire requests.
- A non-200 surfaces as an `upstreamError` so account fallback can try the next connection instead of streaming a provider error page to the client as content.
- Verified with table-driven tests in `internal/proxy/executor/compatible_responses_test.go`: the outbound body carries `input[]` with no `messages[]` leak, the tool declaration is flat with its name and schema intact, an already-Responses body is passed through without being re-wrapped, and a 429 is returned as an error. The first test was confirmed to fail before the fix, reproducing the reported `tool name = ""` and `messages[] leaked to a Responses endpoint`. Full `go build ./...`, `go vet ./...`, `go test ./...` and `make test-integration` pass; upstream `decolua/9router` parity reference is `openaiToOpenAIResponsesRequest` in `open-sse/translator/request/openai-responses.js`, selected there by `resolveOpenAICompatibleApiType`.
