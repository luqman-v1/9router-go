### Changed

- Lower per-request CPU on the SQLite path: prepared statements are now cached per connection (256 entries max, pool of 4) on the one-shot `db.Query`/`db.Exec` paths, instead of being re-parsed by `sqlite3_prepare_v2` on every call. pprof of the request path had put the SQLite parser at ~15% of CPU (~10 statements parsed per request); a repeated point query benchmarks at ~10.7µs vs ~15.2µs before (~30% off). No wire, schema, or endpoint change; the PostgreSQL path is untouched. The explicit `db.Prepare`/`tx.Prepare` path is deliberately uncached (`database/sql` already reuses one driver stmt per connection there, and a cached handle could be finalized under a live `*sql.Stmt` by cap eviction); cached one-shot handles are finalized on connection close. SQLite re-prepares cached statements itself on schema change (`prepare_v2` auto-reprepare, e.g. `ALTER TABLE ... ADD COLUMN`).

Verified with `go test ./internal/db/ -count=1` (incl. a counting driver asserting exactly one engine-level prepare per distinct query on the one-shot paths, and a regression test that a live `*sql.Stmt` still executes after forced cap eviction), `go vet ./...`, `gofmt`, and `-race` on the new tests; benchmark output in PR #1584.
